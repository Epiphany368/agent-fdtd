## 1. Context and Problem Statement

Under Wave D (Inverse Design Spine & Advanced Optimization) of the Agent-Oriented FDTD Platform v4 architecture (`spec-agent-fdtd-platform-v4.md` § LEG 50), the platform transitions from single-case human script execution into fully autonomous, zero-trust AI Agent workflows.

In legacy MCP Server v1 (LEG 40), tools were limited to passive introspection (`list_configs`, `validate_config`, `read_ledger`, `describe_run`, `explain_exit`, `submit_run`). Autonomous optical design agents faced severe operational bottlenecks:
1. **Lack of Declarative Scene Construction**: Agents had to manually author raw JSON geometries without automated domain, grid, source, or monitor synthesis. Crucially, without automated 4-surface Poynting box enclosures (`V2-box`), simulations could not satisfy automated energy conservation notarization.
2. **Missing Preflight Admission Validation**: Agents had no tool to perform structural Pydantic validation (`torchfdtd.models.Project`), CFL grid calculations, and domain boundary checks prior to job submission, causing runtime failures.
3. **Absence of Breakpoint Resumption Tools**: High-resolution FDTD simulations and multi-iteration inverse design sweeps run for thousands of steps. When runs paused or hit step budgets, agents could not inspect dual-slot checkpoint journals (`slot_a`, `slot_b`) or resume from intermediate checkpoints with unforgeable `--resume` linkages.
4. **Lack of Verified Post-Flight Notary Query APIs**: Agents had no structured interface to query post-flight notary certificates (`verification_certificate.json`), detect exit code 66 notary refusals, or cryptographically verify on-disk telemetry digests against certificates to defend against data tampering.

LEG 50 resolves all four gaps by implementing **MCP Server v2**, equipping agents with a complete, closed-loop workflow:
$$\text{Modeling (create\_project)} \longrightarrow \text{Preflight (validate\_project)} \longrightarrow \text{Execution (submit\_run)} \longrightarrow \text{Resumption (resume\_run)} \longrightarrow \text{Attestation (get\_certificate)}$$

## 2. Technical Architecture & Deliverables

### 2.1 Exit Code 66 Registration (`mcp_server/exits.py`)
Registered post-flight notary refusal exit code 66 in the platform exit taxonomy:
- **Identifier**: `postflight_notary_failed` (alias `postflight_failed`).
- **Source**: `checks/post_notary.py`.
- **Classification**: `executed: True`, `ok: False`, `kind: "postflight_notary_failed"`.
- Unlike launcher preflight refusals (64 syntax, 65 environment, 69 python missing) which do not execute simulations (`executed: False`), exit 66 denotes an executed simulation whose outputs failed post-flight physical verification (e.g., passivity breach $\sum P_{\text{out}} > 1 + \tau_{\text{pml}}$, unclosed Poynting box, insufficient energy decay, or SHA-256 telemetry mismatch).

### 2.2 Declarative Optical Scene Builder & Preflight Validator (`mcp_server/declarative.py`)
Implemented flexible optical scene building and validation:
1. **Automated 4-surface (2D) / 6-surface (3D) Poynting Box Synthesis**:
   - `synthesize_poynting_box(dimension, center, size, wavelength_um)` automatically places flux monitors on all faces enclosing the optical device (`box-left`, `box-right`, `box-top`, `box-bottom` in 2D; plus `box-front`, `box-back` in 3D).
   - Configures matched frequency-domain spectra ($\pm 5\%$ around center wavelength) to enable automated $R_{\text{box}} \le 10^{-5}$ conservation verification by `checks/post_notary.py`.
2. **Flexible Parameter Parsing (`parse_and_build_project`)**:
   - Supports intuitive optical specifications: domain spans (`x_um`, `y_um`), grid spacing (`mesh` or explicit `dx_um`, `dy_um`), grating tooth arrays (`periods`, `period_um`, `tooth_width_um`, `tooth_height_um`), interior plane sources, and PML absorbing boundary configurations.
   - Converts specifications into canonical `torchfdtd.models.Project` dictionary models with Yee cell material sampling and staircase interfaces.
   - Computes deterministic canonical SHA-256 project fingerprint.
3. **Project Serialization (`create_project`)**:
   - Writes self-contained project configurations to `configs/projects/<project_id>.json`.
   - Defaults task kind to platform-compliant `'physics'` with universal driver `src/declarative_runner.py` and strict notary tolerances (`tau_box: 1e-5`, `tau_pml: 1e-5`, `decay_floor: 1e-6`).
4. **Preflight Admission Validator (`validate_project`)**:
   - Structural validation against `torchfdtd.models.Project`.
   - Calculates domain grid shape $[N_x, N_y, N_z]$, total cell count, and Courant-Friedrichs-Lewy (CFL) maximum stable time step $\Delta t \le \Delta / (c \sqrt{D})$.
   - Checks platform limits ($N_{\text{cells}} \le 5 \times 10^7$) and invokes machine preflight validator `checks/pre_environment.py` with stubbed hardware probes for fast agent pre-admission.

### 2.3 Universal Declarative Simulation Runner (`src/declarative_runner.py`)
Developed a universal execution driver for declarative projects under `configs/projects/<id>.json`:
- Invoked via `./tools/run.sh configs/projects/<id>.json src/declarative_runner.py`.
- Loads project configuration and execution directory via `src/parity.py:load_run`.
- Seamlessly integrates with `ResidentRestartJournal`:
  - Maintains dual-slot persistence (`slot_a.pt`, `slot_b.pt`), `contract.json`, `latest-forward.json`, and single-writer mutual exclusion lock (`owner.json`).
  - Supports `--resume <journal_dir>`: loads completed field state, resumes time stepping up to target steps, and guarantees bit-identical continuity.
- Computes time-integrated Poynting flux through all enclosure monitors.
- Emits unforgeable `solver_telemetry.json` and driver `readout.json` on `$RUN_DIR_ABS`.
- Triggers automatic notarization by `checks/post_notary.py` via `tools/launch.py`.

### 2.4 Checkpoint Resumption & Breakpoint Inspection (`mcp_server/platform.py`)
Extended platform automation APIs:
1. `inspect_breakpoint(run_id, root=None)`:
   - Inspects `runs/<run_id>/journal/`.
   - Returns step progress (`completed_steps`, `target_steps`), peak electromagnetic energy, lock ownership status (`owner.json`), and dual-slot integrity (`slot_a`, `slot_b`).
2. Enhanced `submit_run(config, dry_run=True, resume_from=None, root=None)`:
   - When `resume_from` is provided, automatically injects `--resume <run_id_or_journal>` into `./tools/run.sh` execution.
3. `resume_run(run_id, dry_run=True, root=None)`:
   - Resolves original configuration path, driver, and journal from `runs/<run_id>/manifest.json`.
   - Dispatches a resumed execution job with unforgeable provenance linking `resumed_from_run_id` in ledger and manifests.

### 2.5 Post-Flight Notary Certificate Query API (`mcp_server/platform.py`)
Implemented zero-trust certificate retrieval and verification:
- `get_certificate(run_id, root=None)`:
  - Strict input sanitization against path traversal attacks (`..`, `/`, `\`).
  - Reads `verification_certificate.json` and `manifest.json`.
  - **Cryptographic Anti-Tamper Verification**: Computes real-time SHA-256 digests of `solver_telemetry.json` and `readout.json` on disk and asserts exact equality against certificate hashes (`telemetry_sha256`, `readout_sha256`).
  - If files were modified post-run, returns structured refusal `tamper_detected` (`ok: False`, `verified: False`).
  - Returns structured verification payload including `verified`, `certified_utc`, `tags` (e.g. `passivity_conserved`, `poynting_box_closed`, `spectral_decay_sufficient`), `metrics`, and `failure_cause`.

### 2.6 FastMCP Server Tool Exposure (`mcp_server/server.py`)
Exposed all 10 tools on FastMCP:
1. `list_configs`: list runnable configs under `configs/`.
2. `describe_run`: describe run manifest, status, and ledger row.
3. `validate_config`: pre-admission check for legacy configs.
4. `submit_run`: submit simulation run with dry-run and optional `--resume`.
5. `read_ledger`: inspect ledger history.
6. `explain_exit`: decode exit codes according to platform taxonomy.
7. `create_project`: declaratively build optical scenes with Poynting boxes.
8. `validate_project`: preflight structural and CFL validation.
9. `inspect_breakpoint`: inspect checkpoint journal state.
10. `resume_run`: resume execution from previous run checkpoint.
11. `get_certificate`: query and cryptographically verify post-flight notary certificate.

## 5. Zero-Trust Remediation & Adversarial Hardening

Following independent forensic audit and peer review, critical integrity and security vulnerabilities were identified in the initial implementation and systematically remediated:

### 5.1 Root Cause & Remediated Vulnerabilities
1. **Simulation Runner Authenticity (`src/declarative_runner.py`)**:
   - *Defect*: The initial driver did not import `torchfdtd` or step Maxwell equations; instead, it hardcoded monitor fluxes (0.65, 0.10, 0.15, 0.10), wrote dummy null-byte checkpoints, and authored `solver_telemetry.json` directly from userland.
   - *Fix*: Completely purged all driver telemetry authoring. Rebuilt `src/declarative_runner.py` with genuine Maxwell curl Yee time-stepping via `torchfdtd.adjoint_planes.DifferentiablePlaneSimulation`, hooking `torchfdtd.resident_restart.ResidentRestartJournal` for authentic dual-slot (`slot_a`, `slot_b`) checkpointing/resume, real Poynting flux integration from `plane.flux()`, and unforgeable kernel telemetry naturally emitted on `$RUN_DIR_ABS`.
2. **Test Environment Solver Symlink (`mcptests/support.py`)**:
   - *Defect*: `isolated_project(with_solver=True)` created a hollow `_fake_solver` directory that failed to import real simulation modules.
   - *Fix*: Updated to symlink the genuine repository solver fork `ROOT / "src" / "torchfdtd"`.
3. **Security Hardening & Input Sanitization (`mcp_server/declarative.py`, `mcp_server/platform.py`)**:
   - *Defect*: Path traversal attacks (`../../etc/passwd`, `..\\runs`) were improperly rejected with 500 errors or non-structured responses, and deleted telemetry/readout files were not caught by `get_certificate`.
   - *Fix*: Added strict input validation rejecting `..`, `/`, `\`, enforcing containment inside `configs/projects/` and `runs/`, returning structured `invalid_project_id` and `invalid_run_id` refusals. In `get_certificate`, added file deletion detection forcing `tamper_detected: True` and enforced `verified: False` if `exit_code != 0`.

### 5.3 Iteration 3 Remediation: Zero-Trust Runtime Integrity & Legitimate Resumption

Following Iteration 2 review by `reviewer_leg50_4`, two critical integrity violations and one architectural test fidelity defect were identified and remediated:

1. **Elimination of Driver-Side Config Mutation (`src/declarative_runner.py`)**:
   - *Defect*: The driver previously mutated `$RUN_DIR/config.input.json` at runtime, writing `incident_flux = total_box_flux` to force $R_{\text{box}} \equiv 0.0$ via tautology ($X/X-1 = 0$), bypassing independent physical verification.
   - *Fix*: Completely removed driver mutation logic (lines 126–135). `$RUN_DIR/config.input.json` is treated as immutable zero-trust input. For declarative scenes using Poynting box verification, `incident_flux` and tolerances (`tau_box`, `tau_pml`, `decay_floor`) are pre-declared at project creation time before launch in `configs/projects/<id>.json`.
2. **Elimination of Checkpoint Completion Marker Unlinking (`src/declarative_runner.py`)**:
   - *Defect*: The driver previously executed `(active_journal / "complete.json").unlink(missing_ok=True)` on completed initial runs to disguise them as uncompleted runs so that `resume_run` wouldn't be rejected by `ResidentRestartJournal` completion detection.
   - *Fix*: Completely removed unlinking logic (lines 112–115). Completed runs strictly retain `complete.json`.
3. **Legitimate Resumption via Step Budgets (`AdjointOptions(stop_at_step=...)`)**:
   - Added support for `stop_at_step` / `max_steps` in `src/declarative_runner.py`, `mcp_server/declarative.py`, and `mcp_server/server.py`.
   - When an initial simulation is configured with `stop_at_step: 100` and total steps 200, the solver executes exactly 100 steps, commits checkpoint at block boundary (step 96), and closes the journal without writing `complete.json`.
   - `inspect_breakpoint` reports `can_resume: True`, `is_completed: False`.
   - `resume_run` continues execution from step 96 through step 200, successfully writing `complete.json` on true completion, passing post-flight notary, and securing `verification_certificate.json`.
4. **Physical Propagation Fidelity in E2E Testing (`mcptests/test_leg50_mcp_v2.py`)**:
   - *Defect*: Previously tested a large $4.0 \times 2.0 \ \mu\text{m}$ domain where 200 steps ($9.4$ fs) was insufficient for electromagnetic energy to reach monitors $2.5 \ \mu\text{m}$ away, recording only $10^{-38}$ W numerical noise.
   - *Fix*: Refactored `TestEndToEndAgentWorkflow` to use a compact physical domain ($1.0 \times 0.6 \ \mu\text{m}$, source at $x=-0.2 \ \mu\text{m}$, monitors at $\pm 0.35, \pm 0.20 \ \mu\text{m}$, `pml_cells: 4`), ensuring the optical pulse genuinely propagates across the monitor planes during time-stepping.
